# Marsh AI-Powered Insurance Pitch Generator — Case Study Write-Up

## 1. System Architecture
The solution is a single-service FastAPI application that handles both backend processing and frontend serving. This design was chosen specifically to meet the constraints of Render's free tier, avoiding the complexity and overhead of deploying separate microservices.

**Core Components:**
- **Frontend (UI/UX):** A responsive, single-page application built with plain HTML, CSS (Marsh branding), and vanilla JavaScript. It handles the form submission, displays loading animations simulating the pipeline steps, and renders the final generated deck and audit results.
- **Backend Framework:** FastAPI, chosen for its asynchronous capabilities, auto-documentation (Swagger), and fast execution. 
- **LLM Engine:** Integrated via Groq's high-speed API. The system uses a two-tier approach:
  - **Generation Tier:** Uses `openai/gpt-oss-120b` to draft the creative and compelling marketing pitch based on the retrieved context.
  - **Structured Tier:** Uses `openai/gpt-oss-20b` for deterministic tasks like extracting the company profile (industry, risks) and the fallback audit of claims, enforcing strictly structured JSON outputs.
  - **Resilience:** Implemented a retry wrapper (`tenacity`) to gracefully handle rate limits (HTTP 429) and an automatic fallback mechanism to OpenRouter if Groq is unavailable.
- **Vector Search (RAG):**
  - Uses `fastembed` (BAAI/bge-small-en-v1.5) to run embedding models entirely locally in the backend without needing external APIs like OpenAI, reducing costs.
  - Stores precomputed embeddings in a lightweight pickle file (`policy_embeddings.pkl`) to avoid persistent database requirements (like PostgreSQL) for the initial MVP, while designing the system modularly enough to easily swap in `pgvector` later.
  - Uses NumPy for rapid in-memory cosine similarity search for both document retrieval and the first pass of the audit layer.

## 2. Document Processing & Ingestion
The ingestion pipeline is designed as an offline task that processes the 4 provided medical insurance brochures.

- **Extraction:** We use `PyMuPDF` (fitz) because it handles complex PDF layouts (tables, multi-columns) better than standard tools.
- **Chunking:** The text is chunked using a sliding window approach (e.g., 500 words with a 100-word overlap) to ensure that context isn't lost across page breaks or section headings. 
- **Embedding:** Chunks are vectorized into 384-dimensional embeddings and saved along with their metadata (document name, source text) into a pickle file. This allows the backend to instantly load the vector index into memory on startup.

## 3. The "Hybrid" Audit Layer
One of the most complex challenges in generative AI is hallucinations—especially in the insurance sector where a hallucinated coverage benefit could cause serious liability.

Our audit layer solves this through a **Hybrid Approach**:
1. **Traceability First:** Before checking accuracy, every single slide claim generated by the LLM is broken down.
2. **Similarity-First Verification:** For each claim, we first run a fast NumPy cosine similarity search against the policy chunks.
   - If the similarity score is **>= 0.85**, the claim is instantly approved as `SUPPORTED`.
   - If the score is **< 0.60**, it is flagged as `UNVERIFIABLE` immediately.
3. **LLM Fallback:** Only for the ambiguous "middle band" (scores between 0.60 and 0.85) does the system escalate to the LLM (`openai/gpt-oss-20b`) for semantic verification. 

This hybrid design drastically reduces both the hallucination risk and the token cost. By bypassing the LLM for obvious matches or clear misses, we save significant API limits, while relying on the LLM's reasoning only for nuanced phrasing.

When escalated to the LLM, it acts as a strict compliance reviewer, assigning one of four labels:
- `SUPPORTED`: The claim is directly backed by the retrieved text.
- `PARTIALLY_SUPPORTED`: The claim is mostly true but might omit a condition or nuance.
- `UNSUPPORTED`: The claim explicitly contradicts the policy.
- `UNVERIFIABLE`: The claim cannot be proven true or false using the provided policy text (a classic hallucination).

This ensures every pitch slide is strictly grounded in the real PDF documents provided. 

### Advisor Workflow for the Audit Report:
The system calculates an **aggregate `overall_confidence` score** and a strict **`overall_pass` flag** for the entire deck. The deck only "Passes" if there are zero `UNSUPPORTED` or `UNVERIFIABLE` claims. 
- **Approve**: If the deck receives a green "PASS" badge, the advisor can confidently download the `.pptx` and present it to the client immediately.
- **Edit**: If there are `PARTIALLY_SUPPORTED` claims (yellow), the UI displays the exact source clause alongside the claim. The advisor can review the nuance and manually edit the `.pptx` to correct the phrasing.
- **Reject**: If there are `UNSUPPORTED` claims (red), it flags a critical hallucination. The advisor should reject this specific draft and can easily hit "Generate Another Pitch" to prompt a new, safe generation.

## 4. Output Generation
- **Presentation Export:** We use `python-pptx` to dynamically assemble a native `.pptx` file. The backend streams the generated JSON slides into styled PowerPoint shapes, returning a clean, downloadable file directly to the client.
- **Dynamic Content:** The deck structure automatically adapts to the generated content, mapping specific company risks to exact policy benefits.

## 5. Deployment Setup
The application is fully configured to be deployed on Render's free tier. 
- A single `render.yaml` file defines the Web Service.
- A customized `.env` template holds API keys.
- The startup command automatically runs the FastAPI `uvicorn` server, ensuring zero-configuration deployment.

## 6. Known Limitations
1. **Ephemeral File System**: The Render free-tier has no persistent disk. Therefore, any new policy added dynamically via the `/admin/add-policy` endpoint will be lost upon server restart. To make this production-ready, it requires migrating the local `pickle` store to Supabase with the `pgvector` extension.
2. **Model Deprecations**: During development, Groq deprecated the `llama-3.3-70b-versatile` and `llama-3.1-8b-instant` models. We successfully migrated to the new `openai/gpt-oss-120b` and `openai/gpt-oss-20b` reasoning models. To future-proof the application, model IDs are now entirely configurable via environment variables in `config.py`.
3. **Strict TPM Constraints**: Groq's free-tier token-per-minute (TPM) limits originally caused `400 Bad Request` generation failures because reasoning models consume extra tokens while "thinking," easily exhausting the budget. This necessitated our hybrid audit design (to skip LLM calls entirely for obvious matches) and required adding `reasoning_effort: 'low'` and a massive `max_tokens: 5000` tuning to avoid truncation errors during the long pitch generation.

## 7. Evaluation Results (Strict Hybrid Audit)
The pipeline was evaluated against three real-world companies using the corrected strict audit thresholds (`similarity_threshold: 0.85`, `llm_audit_threshold: 0.60`). The strict thresholds effectively force the LLM to scrutinize nuanced claims (falling into the 0.60 - 0.85 similarity band), ensuring high compliance.

*   **Infosys**
    *   **Overall Pass:** False (Overall Confidence: 66.6%)
    *   **Total Claims:** 18 (12 Supported, 2 Partially Supported, 4 Unsupported, 0 Unverifiable)
*   **Zomato**
    *   **Overall Pass:** False (Overall Confidence: 42.86%)
    *   **Total Claims:** 21 (9 Supported, 5 Partially Supported, 7 Unsupported, 0 Unverifiable)
*   **Tata Steel**
    *   **Overall Pass:** False (Overall Confidence: 56.52%)
    *   **Total Claims:** 23 (13 Supported, 1 Partially Supported, 9 Unsupported, 0 Unverifiable)
### Verified Hallucination Catches
Manual review of Zomato's flagged claims confirmed the audit layer correctly caught 
three distinct hallucination patterns:
- **Cross-attribution**: a Care Health claim describing a benefit that actually 
  belongs to a different insurer (ABHI) in the document set
- **Fabricated hybrid products**: a "Frankenstein" policy combining a base plan 
  from one insurer with riders from another, which does not exist as an offering
- **Narrative over-generalization**: the LLM inferring an unstated promise (earnings 
  protection for gig workers) by connecting two true but unrelated facts

### Known Limitation: Retrieval False Negatives
Manual review also identified 3 of Zomato's 7 UNSUPPORTED claims as retrieval 
misses rather than genuine hallucinations — the correct supporting text existed in 
the policy documents (and was successfully retrieved in other test runs, e.g. 
Infosys) but was outranked by a less relevant chunk in this specific query. This 
means Zomato's true hallucination rate is closer to 4 genuine unsupported claims, 
not 7. This points to a concrete improvement path: adding a cross-encoder reranking 
step after initial retrieval, or increasing top-k, would likely resolve this class 
of false negative. We chose not to implement this for the current scope given the 
project's time and free-tier constraints, but flag it as the clearest next 
improvement to the system.
